1. The short version

Exact cannot compile a single component, and its web runtime cannot unmount. So the framework turns every story into a small Exact app, builds that app on demand, and loads it into the canvas as an ES module. Storybook's args, actions and mocks reach the app through the one door Exact has for data, its data seam.

  • Import a .contract file → you get a JSON description of its components (no compile).
  • Open a story → the preview asks the dev server for that component's build; the server generates a root component around it, compiles, bundles and returns a manifest.
  • The preview imports the bundle and starts the app with a bridge that answers "what are my args?", "this action was called" and "give me this data source".
  • Change a control → the running app re-asks its args. No rebuild, no remount.
If you know React Native Storybook: the generated root plays the part of storybook.requires (a generated entry that makes your code reachable), and the on-demand build behind a URL is Metro's lazy bundling. The difference is the unit: one bundle per component, not per app.

2. A real example: Mealdrop

Mealdrop is the food-delivery app the Storybook team uses to show what stories can do, written in React. examples/mealdrop is that app in Contract, with the stories and play functions the original has: 116 stories, 68 for the design system and the app's components, 32 for the pages and their parts, 4 for the page template and 12 that run the whole app. It is the place to look for how something is done, and the rest of this page explains why it works.

3. Exact words you need

4. Six facts about Exact that decide the design

Every odd-looking part of the framework, and every limit you will meet as a user, is the consequence of one row here.

Exact, at the pinned commitSo the framework…
Compiles an app (entry file + app.json), never a lone component.generates a root component per story component and compiles that.
Only the root may own resource, mutation, task.puts the args in a resource and each action in a mutation on the generated root; treats a component that owns data as a root itself.
All data crosses one seam: the runtime calls data.answer(source, args).replaces that function. This is the whole integration surface at runtime.
The web runtime mounts into #exact-root, keeps state in module globals, has no unmount.imports a fresh copy of the bundle per mount; allows one story per document; shows docs stories in iframes.
Nothing reports an action prop's parameter types, except a compile error when a handler is wrong.compiles the root repeatedly, reading the errors, until it fits ("signature inference").
No npm package, no stable API, changes daily.pins one commit, builds its compiler from source, and guards every use of an internal with a check that fails loudly.

5. The moving parts

Three places code runs: Node (inside Storybook's own process), child processes (Exact's Rust compilers and Bun), and the preview iframe. The only channel from browser to server that the framework adds is one HTTP path: exact-assets/<id>/….

6. What a .contract import gives you

vite-plugin.ts load() answers the import with JSON. For examples/basic/app/counter.contract:

export const Counter = {
  __exact: true,
  name: "Counter",
  props: [{ name: "start", type: "number" }, { name: "step", type: "number" }, { name: "changed", type: "action" }],
  inject: [], slot: false, root: false,
  id: "Counter-1d92e34f",                 // name + digest of the file path
  file: "counter.contract",
  defaults: { start: 0, step: 0 },       // stand-ins for args a story leaves out
  manifest: "exact-assets/Counter-1d92e34f/manifest.json",
  revision: "f3a59c1eeb031c91"            // digest of every source of the app
};
  • The props come from parseComponents (node/contract.ts), a small text reader: top-level component Name, then section headers, then name: type lines. It does not run the compiler, so an import is instant and needs no toolchain.
  • arg-types.ts turns the props into controls: string → text, number → number, bool → toggle, enum<…> → select, color → colour, shapes and lists → object editor, action → an Actions entry.
  • TypeScript gets the file through the same parse: the framework is a TypeScript 7.1 content mapper for .contract files (node/mapper.ts), so Meta<typeof Counter> type-checks args with nothing written beside the file.
  • The module watches every Contract source of the app, so any edit gives it a new revision. That is how the preview learns a build may be stale.

7. The generated app

Your component (counter.contract)

component Counter

  state count = start

  view
    row gap=12 align-items="center"

What the framework writes (shadow/__story_Counter-1d92e34f.contract)

use Counter from "./counter.contract"

  step: number

  ok: bool

component Story

Where does a0: number come from?

The source says changed: action, not what it is called with. inferSignatures (node/build.ts) writes the root with handlers that take nothing, runs contract build --json --errors-only, and reads the refusals (refineSignatures, node/contract.ts):

  1. type-call-arity / analyze-action-arity: "takes 0 argument(s), given 1" → the handler gets one parameter, typed with a made-up shape StoryUnknown.
  2. type-argument / type-handler-payload: "expects StoryUnknown, given number" → that parameter is number.
  3. Repeat until it compiles (at most 16 rounds; typically 2–3, about 10 ms each). The result is saved in kept/<id>.json and reused until it stops compiling.
This reads the compiler's English messages with regular expressions. A reworded message would break it; see Known limits.

Components that own data

A component with its own resource/mutation/task, or the first component of a file with routes, cannot be placed inside another root. It is compiled as it is, and its story answers its sources:

export const Seeded = { parameters: { exact: { sources: {
  todos: () => [{ id: '1', title: 'Buy milk', done: false }],
  addTodo: (title) => ({ count: 2 }),
} } } };

8. The data seam

Exact's generated main.js ends with go(start);. storybookEntry (node/build.ts) removes that line and appends an export, so importing the bundle does not boot the app until the preview says so:

export function storybookStart(bridge) {
  data.answer = (source, args) => bridge.answer(source, args);   // the seam
  return Promise.resolve(go(() => bridge.launch(start))).then(() => ({
    journal,
    refresh(source) { /* re-ask every resource whose source is this one */ },
  }));
}

bridge.launch runs the app's start with the page at the address the story names (parameters.exact.location, / by default), because an app with routes reads the page's address as it starts; see Known limits.

The preview's side is bridge() in preview/render.ts:

The app asksThe bridge does
storyArgs()returns the current args (defaults filled in), converted to the wire format
storyAction_changed(3)calls args.changed(3), replies { ok: true }
loadTodos() (any other source)calls parameters.exact.sources.loadTodos(); a promise is awaited; a missing mock is an error naming the source

Wire format

The runtime carries a record as an array in field order, a list as an array, none as null. The build's manifest lists each source's types (sourceTypes, read from the compiler's names.js): "storyArgs": [[], { start: "n", step: "n" }]. preview/wire.ts converts both ways and checks strings, numbers and booleans, because the runtime rejects a whole answer for one wrong leaf without saying which. That check is where messages like args.item should be a record with the fields id, title come from.

9. First render, step by step

  • The manifest fetch is wrapped so the render gives up the moment Storybook tears the story down (unlessAborted, preview/render.ts). Without that, clicking through stories while a first build runs makes Storybook reload the whole preview.
  • A build error is answered as { error } with HTTP 200 and shown as that story's error. The server never crashes on a component that does not compile.
  • ?instance=N makes the browser evaluate the module again. That is the entire "unmount" story: a new runtime each time, the old one left behind.
  • DevTools shows the steps as performance.measure entries: exact:manifest, exact:stylesheet, exact:import, exact:boot.

11. The build and its caches

Builder.build(id) → make() (node/build.ts). A hit at a dashed step skips that step, and at 2 or 3 everything after it.

Why step 6 exists

Exact's own web build (host/web-js/build.mjs) runs the compiler and then places about 130 runtime modules and a boot module around its output. It took 1.3–1.9 s per component. Those modules depend on the app only through the flags the compiler writes and the sources the app asks, so the framework runs Exact's build once per distinct key (stagingKey, node/stage.ts), keeps the result, and afterwards runs only the compiler. The boot module differs by one value (a digest of the app's plan), which bootModule rewrites.

Proof it is equivalent: test/build-equivalence.test.ts builds every example component both ways and requires identical bytes; it runs in CI. STORYBOOK_EXACT_WHOLE_BUILDS=1 turns the reuse off.

Four identifiers

NameDigest ofAnswers
idcomponent name + file pathwhich component (URL and cache key)
revisionevery mirrored source of the app, the manifest, asset statscould a build differ? (coarse: per app)

revision is cheap and pessimistic; version is exact. An edit anywhere in the app triggers a rebuild of open components (cheap), and only those whose bytes changed remount.

Why a shadow copy

  • The generated root must sit at the app's top level: a use may not leave the app directory.
  • Exact's build would otherwise compile the app's own app.ts, Rust and native modules. The shadow's app.json drops those keys.
  • Nothing generated lands in your source tree.
  • A library is not mirrored: the shadow is an empty app with the package symlinked into node_modules, because Exact applies a package's tokens only when it is used by name.
  • The app's design file is named in the shadow's manifest, because Exact only finds app.tamber by itself beside a file called app.contract.

12. Questions

Why does the first run take minutes?

Exact has no published package, so the first storybook dev fetches it at one pinned commit and builds its compiler with Cargo. That happens once per machine (a minute or two with a warm Cargo cache) and lands in ~/.cache/storybook-framework-exact, never in your project. npx storybook-exact setup does it ahead of time, in CI for example, and the exactRoot option uses a checkout you already have (README, "Getting Exact").

Does it write anything into my app?

No. Builds happen in a copy of your Contract sources and assets under node_modules/.cache, and TypeScript reads your Contract files directly (next question).

How are a story's args typed?

From the component's props, read from the Contract file each time TypeScript looks. TypeScript 7.1 (in beta) lets a package say how a file that is not TypeScript reads as TypeScript, and the framework does that for .contract files: you name it under contentMappers in tsconfig.json and run tsc --runExternalCode. A wrong or misspelt arg is an error in the story, a shape taken from another Contract file is checked too, and Go to Definition on an arg opens the prop in the Contract file. With an older TypeScript the framework writes a .d.contract.ts beside each file instead (README, "Types"). This part is an experiment on a beta.

Is the component in my story the one my app ships?

Yes. The generated root around it is ordinary Contract, and Exact's own compiler and runtime build it. The framework changes two things only: when the app starts, and who answers its data. The framework reuses the runtime modules between builds to be fast, and a test in CI holds that to the same bytes as Exact's whole build. What a story leaves out is the rest of your app: its app.ts, Rust and native modules are not built, so a component that owns data gets it from the story's mocks.

Why is there a short wait the first time I open a component?

A component is built when you open one of its stories, not when Storybook starts: about 35–100 ms, and about a second for the first component of an app. Builds are kept on disk, so after a restart only what changed is built again. Switching between built stories takes about 50 ms.

Does changing a control rebuild the component, or lose its state?

Neither. The args are a resource of the running app, and a control change asks the app to read it again. A counter you clicked up stays where it is while you change its step.

One of my components does not compile. Does that break Storybook?

In storybook dev, no: the error shows in that component's stories and the rest run. storybook build fails if a story imports that component, and leaves it out (and says so) if none does.

Why is each story on a docs page in an iframe?

Exact's web runtime mounts one app per document, into a fixed element, and cannot unmount. So a page with several stories needs several documents. Give a tall component room with parameters.docs.story.height.

Why can't a decorator wrap my component in markup?

A story is an Exact app that paints itself, not DOM that the story returns, so there is nothing for a decorator to wrap. A decorator can still change args and parameters, or the document around the app (that is how the colour scheme toolbar works). To wrap a component, or to give a slot real children, write a small Contract component that does it and write the story for that.

How do I show a component that loads data, or a whole app with routes?

Such a component is built as it is, and its story answers its sources: parameters.exact.sources maps each source name to a function (see Components that own data). An app with routes starts at /, or at parameters.exact.location. The Mealdrop example runs a whole ordering flow this way, play functions included.

Will it work with the newest Exact?

It works with the commit it pins. Exact changes daily and the framework relies on a few of its internals, each behind a check, so a newer Exact that moved one fails with "This Exact revision is newer than storybook-framework-exact supports" instead of misbehaving. Moving the pin is a new release of the framework.

Does it show my components on iOS and Android?

No. Stories show Exact's web target only.

Is this an official Storybook or Expo package?

Neither. It is a community framework in its own repository, so it can follow Exact's pace while Exact is pre-1.0.

Exact has a gallery. Why Storybook?

They do different jobs; see How it compares.

13. Known limits

The README's Limitations is the list to check before you adopt it. These are the ones that come from how it works:

  • One story per document. Docs pages use iframes, and each story you open starts a fresh copy of the runtime. Earlier copies are not disposed until the preview reloads, so a very long session holds on to their memory and timers. How much has not been measured.
  • Decorators cannot wrap markup, and a component with a slot is shown with a line of placeholder text in it.
  • What an action prop is called with is worked out from compiler errors. Exact does not report it, so the framework compiles the generated root, reads the refusals and corrects it. A reworded compiler message would break this; the pinned commit and a test against the real compiler guard it. If it fails for a component, its stories show "Could not work out what … action props are given".
  • Props are read from the source text, not by the compiler, so that imports are instant. It expects source laid out as Exact's formatter leaves it; props brought in through members may be missed (not tested).
  • An edit rebuilds every component of the app you have open. Fine at 35 ms each; it has not been tried with hundreds open.
  • Dark mode follows the browser unless a decorator sets the document's color-scheme, which every token follows (README, "Colour scheme").
  • An app with routes shares the tab's history. Its visits are real history entries, written without their addresses: the canvas keeps Storybook's address, a reload shows the story, and the browser's Back and Forward step through the app (preview/address.ts). The runtime of a story you opened earlier still listens to those steps; what it does with them has not been examined.
  • It relies on Exact internals: how the generated main.js boots, what rt.js and names.js export, which files the compiler writes. Each has a check that fails loudly, and each may need a fix when the pin moves.
  • Web only, on macOS and Linux. Windows has never been run.

14. What would lift them

Most of the limits are Exact's, and two additions to Exact would remove most of the machinery on this page. Neither exists at the pinned commit, and nothing here is a promise.

  • A way to describe a component (its props, what its actions are called with, its slot and injected values). The text reader and the reading of compiler errors would go.
  • An unmount, or a choice of root element, in the web runtime. Docs stories could render inline, and nothing would be left behind between stories.

In the framework itself: rebuild only the components an edit affects, share the runtime modules between apps (each library pays 0.3–0.6 s once today), and dispose of earlier runtimes.

15. How it compares

Exact's own gallery

Exact has contract gallery, part of its design tool: a generated second app, served by the dev loop at /__dev/gallery/, that places each exported library component the app uses once per variant value (the first value of every variant prop, then each other value alone, never combinations), with placeholders for every other prop and no-ops for actions. Nobody writes it, and it follows each kept token edit. It does not show an app's own components, chosen args or data. What it lacks is what Storybook is: args with controls, action logs, play functions and interaction tests, docs pages, addons (a11y, viewports, visual tests) and a static site to publish. Its dev loop rebuilds the whole app and reloads on an edit; a story's hot update rebuilds one component and keeps the controls.

What the gallery has that this does not: nothing to write, nothing generated around your component, no pinned version, and it is part of the tool that edits your tokens. Use it to look over a library's variants; use stories for chosen states, data, interaction tests and docs.

16. See it for yourself

In your own project, with storybook dev running:

  • The generated root of a story: node_modules/.cache/storybook-framework-exact/<app>-*/shadow/__story_*.contract
  • What is remembered between runs: …/kept/<id>.json (stamp, revision, manifest, signatures)
  • The protocol: Network tab, filter exact-assets: one manifest.json?r=…, one style.css, one bundle.js?instance=N per mount.
  • The time each step takes: Performance tab, Timings track, exact:*. On the server, the log line exact: Built Counter (counter.contract) in 35 ms.
  • The errors: put a typo in a component (an error in its stories only); remove a mock from the story of a component that owns data (the error names the source); give an arg the wrong type (the error names the field).
  • Where Exact and the cache are: npx storybook-exact where
